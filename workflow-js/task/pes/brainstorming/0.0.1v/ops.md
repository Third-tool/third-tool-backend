## [후보 1] SLO/SLI 정의 + 대시보드 연결

> "P95 < 500ms" 같은 정량 약속을 사용자 경험과 코드에 동시에 박는다.

### 배경
- `product-load-test.md`에 baseline 4개 API의 P95 임계가 명시 (예: `/today` < 500ms).
- 그러나 **운영 중 실측 P95를 매일 확인하는 대시보드·알림은 미명시**.
- `product-op.md` v2가 Prometheus·Grafana 도입 명세지만 v1으로는 미진입.

### 후보
- **A안**: Prometheus + Grafana로 SLO 보드 즉시 도입. 장점: 표준. 비용: 인프라 시간.
- **B안**: AWS CloudWatch 메트릭으로 시작. 장점: AWS 사용 시 기본 제공. 비용: 시각화 제한적.
- **C안**: 응답 시간 로그를 일 1회 집계 메일. 장점: 인프라 0. 비용: 실시간성 X.

### 1차 권장
B안 → A안 점진. CloudWatch로 즉시 임계 알림부터 가동, Grafana는 사용자 N명 증가 시점에.

### PES 승격 경로
- `product-op.md` v1 진입 — 본 후보가 그 트리거
- `product-infra-ops.md`에 모니터링 Epic으로 흡수

### 미해결 질문
- 현재 운영 환경이 AWS인지 / 다른 클라우드인지 확인 필요.

## [후보 2] 인시던트 대응 runbook

> 사고 발생 시 "무엇을 보고 → 무엇을 결정 → 누구에게 알림" 체크리스트를 미리 적어둔다.

### 배경
- 1인 운영. 사고 발생 시 당황·의사결정 지연·재현 절차 망각 위험.
- 5xx 응답에 `X-Request-Id`가 있어도 그걸 추적해서 어디로 가야 하는지 절차가 없음.

### 후보
- **A안**: `docs/runbooks/` 디렉토리 + 시나리오별 (DB 다운 / RT 탈취 의심 폭증 / 5xx 폭증) MD 작성. 장점: 사고 시 즉시 참조. 비용: 시나리오 발굴 시간.
- **B안**: Notion·외부 도구. 장점: 검색·인덱스 풍부. 비용: 동기화 부담.
- **C안**: 현재 상태 (사고 시 그때그때 대응). 비용: 동일 사고 반복 시 대응 시간 누적.

### 1차 권장
A안. 시나리오는 최소 3개로 시작 (DB · 인증 · 5xx). 사고가 실제로 발생할 때마다 새 runbook 추가.

### PES 승격 경로
- ADR 후보: "인시던트 대응 프로세스" (1인 운영 가정)
- `product-infra-ops.md`에 흡수

## [후보 3] 헬스체크 깊이 확장

> `/health`가 단순 OK가 아니라 "DB·외부 의존성 모두 정상" 여부를 반환.

### 배경
- 현재 `HealthCheckController` → `GET /health`는 `ResponseEntity.ok("OK")` 만 반환.
- DB 연결 끊김 / Spring AI 어댑터 실패 / 외부 OAuth provider 다운을 감지하지 못함.
- FE 측 `/maintenance` 페이지 이동 트리거가 `/health` 503 가정인데, 단순 OK는 false negative.

### 후보
- **A안**: Spring Boot Actuator `/actuator/health`로 교체 + DB·외부 의존 indicator 등록. 장점: 표준. 비용: `product-op.md` v2 활성화 필요.
- **B안**: 자체 `/health/deep` 엔드포인트 추가 — DB ping + 외부 의존성 timeout 짧게 체크. 장점: Actuator 정책 별개. 비용: 자체 작성.
- **C안**: 현재 상태 유지. 비용: 부분 장애 미감지.

### 1차 권장
A안. `product-op.md` v2 활성화와 함께 묶어서 진행 (Actuator를 켜면 prometheus·info·health 모두 정책 결정 필요).

### PES 승격 경로
- `product-op.md` v1 진입 — 후보 1과 함께 묶음

## [후보 4] 비용 모니터링 (AWS Cost Explorer + 예산 알림)

> 월 비용 임계 초과 시 즉시 인지.

### 배경
- 1인 사이드 프로젝트 — 비용 통제가 운영 지속성의 핵심.
- AWS Cost Explorer / Budgets 알림이 설정되어 있는지 확인 필요.
- LLM 비용은 별도 (ai.md 후보 5).

### 후보
- **A안**: AWS Budgets로 월 한도 + 80% 도달 시 메일. 장점: AWS 네이티브. 비용: 0.
- **B안**: 일 1회 Cost Explorer API 호출 + Slack/메일. 장점: 세분화. 비용: 작성 시간.
- **C안**: 현재 상태 (매월 청구서 직접 확인). 비용: 알림 지연 위험.

### 1차 권장
A안. 즉시 활성화.

### PES 승격 경로
- ADR 후보 (Product화 불요): 월 한도 결정
- `product-infra-ops.md`에 한 줄 추가 가능

## [후보 5] 용량 산정 모델

> 사용자 N명·카드 M장 시점의 RDS 사양·EC2 사양을 표로 정리.

### 배경
- 사용자가 늘면 어느 시점에 어떤 리소스를 키워야 하는지 가이드 없음.
- 부하 테스트(`product-load-test.md`)는 baseline P95 측정만 다룸 — 확장 시뮬레이션은 미명시.

### 후보
- **A안**: 100명 / 1,000명 / 10,000명 시나리오별 권장 사양 + 월 비용 표. 장점: 미리 준비. 비용: 작성 시간 + 가정 정확도 한계.
- **B안**: 실제 사용자 N명 도달 시점에 측정 기반 산정. 장점: 정확. 비용: 사후 대응이라 사고 위험.
- **C안**: AWS Auto Scaling으로 자동화. 장점: 사람 결정 최소화. 비용: 비용 폭증 위험 (특히 RDS).

### 1차 권장
A안. 가정 기반이라도 미리 적어두면 사고 시 의사결정 빠름.

### PES 승격 경로
- `product-load-test.md`에 "용량 산정 시나리오" Epic 추가

## [후보 6] 보안 모니터링 (RT 재사용 / 비정상 로그인)

> 인증 사고 패턴을 운영 중 자동 탐지.

### 배경
- `REFRESH_TOKEN_REUSED` ErrorCode가 도입되어 있음 (Story 3-2).
- 그러나 **그 이벤트가 운영 중 얼마나 자주 발생하는지·어느 사용자에게 집중되는지 가시화는 미명시**.
- 동일 IP에서 다른 계정 다수 로그인 시도 같은 패턴 탐지도 없음.

### 후보
- **A안**: 인증 실패 로그를 별도 메트릭으로 수집 → 임계 초과 시 알림. 장점: 즉시. 비용: 로그 패턴 정의 시간.
- **B안**: 외부 SIEM 도입 (Datadog Security 등). 장점: 풍부. 비용: 인프라 비용 큼.
- **C안**: 현재 상태. 비용: 탈취 의심 사고 발견 늦음.

### 1차 권장
A안. 후보 1 (SLO 대시보드)과 같은 인프라(Cloudwatch 또는 Prometheus) 위에서 작성.

### PES 승격 경로
- `product-auth.md`에 "보안 모니터링" Epic 추가 또는 ADR 후보

## [후보 8] `/actuator/prometheus` v1 활성화 일정

> `product-op.md` v2 표시된 항목을 언제 v1으로 끌어올릴지.

### 배경
- `product-op.md`는 actuator 노출 정책을 명세하지만 v1에서는 비활성.
- 본 카탈로그의 후보 1·3·6이 모두 메트릭 노출을 전제로 함 — actuator 활성이 그 전제.
- "v2"라는 라벨이 영구적으로 떠있을 위험.

### 후보
- **A안**: 후보 1 (SLO) / 3 (헬스체크 깊이) / 6 (보안 모니터링) 중 하나라도 진입하면 actuator도 함께 활성. 장점: 묶음 진행. 비용: 묶음 결정.
- **B안**: actuator만 단독으로 먼저 활성 + 메트릭은 점진 노출. 장점: 단계적. 비용: 활성된 채 사용 안 되는 기간.
- **C안**: 현 상태 유지. 비용: 후보 1·3·6 모두 멈춤.

### 1차 권장
A안. 본 카탈로그의 후보 1과 함께 묶음 진행 권장.

### PES 승격 경로
- `product-op.md` v1 진입 — 본 카탈로그 후보 1·3·6과 묶음
