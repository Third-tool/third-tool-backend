# meta

> 목적: `docs/`가 담당하지 않는 AI 활용 실험·자동화·skill 운영·사용법·사용 결과·최소 배포(문서 배포) 기록을 관리하는 영역.
>
> 핵심 태도: 팀원에게 방식을 강요하지 않고, `이런 방법을 써봤더니 이런 결과가 나왔다`를 축적해 **자연스럽고 가장 싼 가격의 AX 환경**을 설명한다.

## meta 와 docs 의 경계

### `docs/`가 전담하는 것
면접관·리뷰어·프로젝트 이해관계자가 **프로젝트 내부를 이해하기 위해 직접 궁금해할 것들**은 `docs/`에서만 관리한다.

예:
- ADR
- 아키텍처 설명
- 트러블슈팅
- living-docs
- 도메인 의도 / 패키지 구조 / 설계 결정
- 프로젝트 안에서 `왜 이렇게 만들었는가?`에 답하는 문서

즉, **ThirdTool 자체의 truth / rationale / reviewer-facing evidence** 는 `docs/`의 책임이다.

### `meta/`가 담당하는 것
`meta/`는 프로젝트 바깥으로도 설명 가능한 **작업 방법·도구 활용·AX 실험·문서 배포용 중간 산출물**을 관리한다.

예:
- topic 작업 생산성을 올리는 자동화
- agent / prompt / workflow / harness / skill 운영 방식
- 실제 사용법, 사용 결과, 버전별 개선 기록
- 로컬에서 혼자 먼저 써보는 AX 실험
- 아직 정식 제품/플러그인/서비스로 배포하지 못했지만 문서로는 공유할 가치가 있는 것
- Velog 글로 배포할 주제의 초안 / 근거 / 결과 정리

즉, **"프로젝트를 더 잘 일하게 만든 방법"** 과 **"AI를 이렇게 써보니 이런 효과가 있었다"** 를 축적하는 곳이다.

## 저장 원칙

### 1. 강요하지 않고 제안한다
`meta/`의 문서는 팀 표준을 강제하는 문서가 아니다.

반드시 다음 관점을 유지한다:
- 우리가 이 방법을 왜 시도했는가
- 어떤 상황에서 편했는가
- 어떤 비용/한계가 있었는가
- 누구에게 추천할 수 있는가
- 아직 로컬 실험 단계인지, 반복 사용 단계인지

문체는 `반드시 이렇게 하자`보다
`이렇게 해보니 이런 결과가 나왔고, 이런 상황에서는 유용했다`에 가깝게 쓴다.

### 2. 결과 없는 아이디어만 쌓지 않는다
`meta/`는 아이디어 저장소가 아니라 **사용 흔적이 남는 운영 저장소**다.

가능하면 항상 함께 남긴다:
- 사용 맥락
- 적용 방법
- 관찰된 장점
- 실패/한계
- 다음 버전에서 바꿀 점

즉, "좋아 보이는 생각"보다 **"실제로 써본 방법 + 결과"** 를 우선한다.

### 3. 로컬 우선, 문서 배포로 최소 확산
여건상 정식 배포를 못 하더라도 다음 순서는 허용한다:
1. local 에서 혼자 사용
2. `meta/`에 사용법과 결과 축적
3. Velog 에 버전별 글로 외부 공유

정식 패키지/서비스 배포를 못 했다는 이유로 버리지 않는다.
대신 **문서 배포**를 최소 배포 방식으로 인정한다.

### 4. `docs/`의 truth 를 다시 쓰지 않는다
`meta/`는 `docs/`의 내용을 복제하는 곳이 아니다.

- 프로젝트 구조 설명, ADR 요약, 트러블슈팅 본문을 `meta/`에 다시 쓰지 않는다.
- 필요하면 `docs/`를 링크하고, `meta/`에는 그 문서를 만들거나 유지하는데 사용한 방법/자동화/활용 경험만 남긴다.

예:
- 허용: `roadmap 수렴/발산 agent로 docs 갱신을 더 쉽게 만든 과정`
- 비허용: `프로젝트 아키텍처 자체 설명을 meta 에 중복 정리`

## meta 의 2갈래 운영 모델

`meta/`는 각 주제를 **두 갈래 문서**로 운영한다.

### 1) Facade 문서
현재까지의 설명을 한 번에 볼 수 있는 **대표 문서**다.

역할:
- 이 주제가 무엇인지 빠르게 설명
- 왜 이걸 쓰는지 요약
- 현재 운영 방식과 핵심 흐름 요약
- 최신 상태를 한 눈에 보여주는 entrypoint 역할
- 세부 버전 문서와 Velog 문서로 들어가는 입구 역할

즉, Facade 문서는
**"지금 이 주제를 처음 보는 사람이 가장 먼저 읽는 문서"** 다.

### 2) Version 문서
버전마다 무엇이 달라졌는지, 실제로 어떻게 썼는지, Velog 에 어떤 글을 썼는지 남기는 **이력 문서**다.

역할:
- `0.0.1v`, `0.0.2v` 식으로 버전별 snapshot 보관
- 그 버전에서 무엇을 시도했고 무엇을 얻었는지 기록
- 사용 결과 / 장점 / 실패 / 한계 / 다음 버전 트리거 정리
- 해당 버전과 연결된 Velog 글 초안 또는 발행 링크 연결

즉, Version 문서는
**"이 주제가 어떻게 진화했는지 보여주는 변경 이력 + 사용 결과 문서"** 다.

## 디렉토리 구조 규칙

각 주제는 패키지 단위로 만들고, 그 안을 아래 2갈래로 운영한다.

```smalltalk
meta/
└── <package-name>/
    ├── README.md              "Facade: 현재까지의 설명"
    └── versions/
        ├── 0.0.1v.md          "해당 버전의 사용 결과 / 변화 / Velog 연동"
        ├── 0.0.2v.md
        └── ...
```

핵심 원칙:
- `README.md`는 항상 최신 요약 상태를 반영하는 Facade 다.
- `versions/*.md`는 과거와 현재의 버전별 snapshot 이다.
- 어떤 주제를 처음 설명할 때는 `README.md`를 본다.
- 어떤 버전에서 무엇을 했는지 보려면 `versions/`를 본다.

## Facade 문서 규칙 (`README.md`)

각 패키지의 `README.md`는 최소 아래를 가진다:
- 이 주제가 다루는 문제
- 왜 이게 `docs/`가 아니라 `meta/`에 있어야 하는지
- 지금 이 방법을 어디에 어떻게 쓰고 있는지
- 현재 기준 핵심 사용 흐름
- 현재까지 확인된 기대 효과
- 현재까지 확인된 한계 / 실패 비용
- 버전 문서 목록
- Velog 연동 상태

권장 톤:
- 설명은 현재형으로 쓴다
- "지금 우리는 이걸 이렇게 쓰고 있다"를 보여준다
- 세부 히스토리를 길게 적기보다, 상세는 `versions/`로 보낸다

## Version 문서 규칙 (`versions/0.0.Nv.md`)

각 버전 문서는 최소 아래를 가진다:
- 이 버전에서 무엇을 시도했는가
- 왜 바꿨는가
- 이전 버전 대비 무엇이 달라졌는가
- 실제 어디에 적용했는가
- 편해진 점 / 안 맞았던 점
- 실패 / 한계 / 비용
- 다음 버전 트리거
- Velog 초안 여부 또는 발행 링크

파일명 규칙:
- `0.0.1v.md`
- `0.0.2v.md`
- `0.0.3v.md`

문서 제목 예시:
- `# 0.0.1v - roadmap 수렴/발산 agent 첫 적용`
- `# 0.0.2v - docs 갱신 자동화 범위 확장`

즉, 파일명은 버전으로 정렬하고,
문서 제목에서 그 버전의 핵심 변화를 설명한다.

## Velog 연계 규칙

Velog 는 `meta/`의 외부 배포 채널이다.
하지만 source of truth 는 여전히 repo 내부 문서다.

운영 방식:
- 내부 운영 기준과 상세 근거는 `README.md` + `versions/*.md`에 남긴다.
- 외부 공개용으로 다듬은 버전은 Velog 에 발행한다.
- 발행했으면 해당 버전 문서에 링크를 남긴다.
- 아직 발행 전이면 초안 상태라고 명시한다.

권장 방식:
- `README.md`에는 "현재 Velog 발행 상태"만 간단히 요약
- 실제 Velog 링크와 버전별 대응 관계는 각 `versions/*.md`에 기록

예:
- `0.0.1v.md` → Velog 초안 작성 완료, 미발행
- `0.0.2v.md` → Velog 발행 완료: <링크>

## 언제 README 를 고치고, 언제 버전을 올리나

### README 를 고치는 경우
다음은 Facade 갱신이다:
- 현재 설명이 달라짐
- 현재 사용 흐름이 달라짐
- 지금 기준 추천 방식이 바뀜
- 최신 버전 기준 핵심 요약을 다시 써야 함

즉, `README.md`는 **현재 정답**을 유지하는 문서다.

### 새 버전을 만드는 경우
다음은 Version 추가다:
- 사용 방식이 눈에 띄게 바뀜
- 자동화 범위가 넓어짐
- 품질/속도/운영 경험이 달라짐
- 실패/제약에 대한 이해가 갱신됨
- Velog 로 외부 공유할 만큼 의미 있는 snapshot 이 생김

즉, `versions/*.md`는 **변화의 흔적**을 남기는 문서다.

## `meta-velog/` 비공개 drafting 패키지

`meta/` 아래에는 별도로 `meta-velog/`를 둘 수 있다.

역할:
- 외부 공개용 Velog 글 초안 작성
- 설명 / 사용법 / 결과 / 버전 업데이트 글 정리
- AI와 함께 문장·구성·제목 후보를 다듬는 로컬 작업 공간

중요:
- `meta-velog/`는 `.gitignore` 대상이다.
- 초안, 메모, 미완성 글감은 GitHub에 올리지 않는다.
- 면접관/외부에는 필요 시 최종 결과 글만 보여준다.

권장 구조:

```smalltalk
meta/
└── meta-velog/
    ├── README.md
    ├── ai-recommendation/
    │   ├── README.md
    │   ├── 0.0.1v.md
    │   └── 0.0.2v.md
    ├── question-maker/
    │   ├── README.md
    │   └── 0.0.1v.md
    └── ...
```

운영 원칙:
- `meta/`는 내부 운영 기록
- `meta-velog/`는 외부 공개용 글 drafting
- 같은 주제라도 source of truth 는 `meta/` 쪽에 두고, `meta-velog/`는 외부 전달용 표현을 다듬는 층으로 둔다

## 금지 규칙

다음은 `meta/`에 두지 않는다:
- 프로젝트 아키텍처 truth 자체
- 도메인 설계 결정의 최종 근거
- 면접관 대응용 핵심 프로젝트 설명 문서
- 단순 일기성 메모만 있는 문서
- 실제 사용 없이 아이디어만 나열한 문서
- 팀 표준으로 확정되지 않았는데 강제 규약처럼 쓰인 문서

## 운영 한 줄 요약

`meta/`는
- `README.md`로 **현재까지의 Facade 설명**을 유지하고,
- `versions/0.0.Nv.md`로 **버전별 사용 결과와 Velog 연동 이력**을 축적하고,
- 필요하면 `meta-velog/`에서 **비공개 외부 공개용 글 초안**을 따로 다듬는

**AX 운영 + publishing 분리 문서 영역**이다.
