## 2. 도메인 모델 이해 — "조합형"은 어디에 있는가

현재 계층 구조에서 "조합형 컨셉 로드맵"을 구현할 수 있는 레이어가 **두 곳** 존재한다.

```
Option X: Facade 레벨에서 조합
─────────────────────────────
[Facade: "풀스택 PM"]
  ├── Axis: 백엔드 역량
  │     ├── Topic: Java 심화
  │     └── Topic: DB 설계
  ├── Axis: 디자인 역량
  │     └── Topic: Figma UI
  └── Axis: PM 역량
        └── Topic: PRD 작성

=> 1 Facade 안에서 다도메인 조합 가능
   (현행 구조로 이미 지원됨)

Option Y: Facade 레벨이 도메인 단위
────────────────────────────────────
[Facade A: "백엔드 개발자"]
  └── Axis: Java, DB, API, 인프라...

[Facade B: "프로덕트 디자이너"]
  └── Axis: UX, Figma, 유저 리서치...

=> 조합 = 여러 Facade를 동시에 운영
   (현행 UNIQUE 제약 위반 → 변경 필요)
```

**결정의 본질**: "조합형"을 Axis 레이어로 표현할 것인가, Facade 레이어로 표현할 것인가.

---

## 3. "1개 유지 (A)" 근거

### 3.1 도메인 응집도 — Facade = 단일 직업 정체성
- LearningFacade의 의미는 "나는 무엇을 배우는 사람인가"의 루트.
- 조합은 Axis(축)로 표현: "백엔드+디자인+PM"을 동시에 배우고 싶다면 3개 Axis를 하나의 Facade 아래 두면 된다.
- 이 경우 Facade가 "풀스택 PM"이라는 통합 정체성을 표현하고, Axis가 구체적 도메인을 분리. **조합형 로드맵이 이미 지원된다.**

### 3.2 카드(Card)와의 관계 일관성
- `Card`는 현재 `Deck`에 종속. `Deck`이 LearningFacade에 간접 종속인 경우 여러 Facade는 Card BC 소유권을 복잡하게 만든다.
- 1 Facade = 1 "컨텍스트"이므로 모든 Card가 단일 트리 안에서 의미를 갖는다.

### 3.3 UX 인지 부하
- 유저가 Facade를 고를 필요가 없다. 진입하면 항상 "나의 학습 트리" 하나가 펼쳐진다.
- 목적지가 명확: 어디에 자료를 붙이든, 어떤 카드를 만들든 같은 Facade 안.

### 3.4 구현·운영 단순성
- BE: UNIQUE 제약 1개, Application Service 선체크 1회. 현행 코드 변경 없음.
- FE: 활성 Facade 선택 UI 없음. 자동으로 유저의 유일 Facade로 진입.
- DB 인덱스·FK 관계가 단순.

### 3.5 포커스(Focus) 원칙과의 정합
- 제품 철학이 "한 가지 직업 컨셉을 깊이 파는 것"이라면 1개 제약은 철학의 구현체.
- 여러 Facade를 동시에 운영하면 사용자의 에너지가 분산된다 — 의도된 제약이 UX 가이드가 될 수 있다.

## 4. "다수 허용 (B)" 근거

### 4.1 실제 학습자 행동 패턴
- "나는 백엔드 개발자 + UI 디자인을 같이 배운다"는 현실적 조합이다.
- Axis로 묶으면 "백엔드 개발자이면서 디자인도 배운다"는 뉘앙스. 디자이너가 되는 로드맵과 백엔드 로드맵은 **목표·우선순위·마일스톤이 다르다** — 같은 Facade 안에 묶기 어색할 수 있다.

### 4.2 커리어 전환 시나리오
- "현재: 백엔드 개발자 Facade → 전환 목표: PM Facade" 시나리오에서
  - 1개 제약: 기존 학습 트리 전체 삭제 후 새 Facade 생성. 과거 학습 이력이 사라짐.
  - 다수 허용: 두 Facade 병존 → 활성 전환 또는 동시 운영.
- 조합형 로드맵의 핵심은 **과거 컨셉을 보존하면서 새 컨셉을 추가**하는 것이다.

### 4.3 "조합형" 컨셉 로드맵의 정확한 의미
- "조합형"은 단순히 여러 Axis를 한 Facade에 묶는 것이 아닐 수 있다.
- 예: "백엔드 개발자로서 성장하는 로드맵"과 "사이드프로젝트 PM으로 성장하는 로드맵"은 **독립된 맥락**이다. 이걸 하나의 Facade에 묶으면 컨셉이 흐릿해진다.
- 각 Facade가 **독립된 목표/정체성**이고, 유저가 여러 정체성을 동시에 개발한다면 다수 Facade가 더 정확한 모델.

### 4.4 Axis 레이어의 표현 한계
- Axis는 "학습 차원(dimension)"이지 "학습 목적(purpose)"이 아니다.
- 예: `Axis: 백엔드`가 있어도 그 안의 Topic들이 "PM 업무를 위한 백엔드 이해"와 "백엔드 개발자 취직을 위한 심화"를 동시에 담기엔 의미가 섞인다.
- 목적이 다르면 Facade를 분리하는 것이 더 명확한 설계.

### 4.5 제품 차별화 관점
- 기존 학습 도구(Notion, Obsidian, Anki)와의 차이가 "내 직업 컨셉 단위 로드맵"이라면, 여러 컨셉을 동시에 관리하는 것은 경쟁 우위.
- 1개 제약은 "v1 단순화"이지만, 제품이 성숙하면 반드시 부딪히는 제약이다.

## 5. "조합형 컨셉 로드맵" 관점 특이 분석

> 이 섹션은 단순 1개 vs 다수 논쟁을 넘어 **"조합형"이라는 제품 컨셉에서 어떤 모델이 더 정합한가**를 분석한다.

### 5.1 조합의 레벨 정의

| 조합 레벨 | 의미 | 구현 위치 |
| --- | --- | --- |
| **축(Axis) 조합** | 한 컨셉 안에서 여러 학습 차원 조합 (예: Java + DB + 인프라 = 백엔드) | 현행 Axis 다수로 지원됨 |
| **목적(Purpose) 조합** | 서로 다른 커리어 목적을 동시에 추구 (예: 개발자 + 디자이너) | Facade 다수가 필요함 |
| **시간 조합** | 과거 컨셉 → 현재 컨셉 → 미래 컨셉을 히스토리로 관리 | 하이브리드(C)가 적합 |

**핵심 질문**: 이 제품에서 "조합"은 어떤 레벨인가?

- **축 조합만이 목표**: 1개 Facade 유지 (A). Axis를 다양하게 두는 것으로 충분.
- **목적 조합까지 목표**: 다수 Facade 허용 (B). 독립 컨텍스트 운영.
- **시간 조합(히스토리)이 목표**: 하이브리드 (C). active 1개 + archived N개.

### 5.2 "조합형 컨셉 로드맵"에서 Facade 1개 모델의 한계 시뮬레이션

```
시나리오: 유저가 "백엔드 개발자 취직"과 "사이드프로젝트 디자인" 두 로드맵 동시 관리

[1개 Facade 모델]
Facade: "멀티플레이어 개발자"
  Axis: 백엔드 취직 준비
    Topic: Spring Boot 심화
    Topic: CS 면접 준비
  Axis: 사이드프로젝트 디자인
    Topic: Figma 기초
    Topic: UX 리서치

→ 문제: 두 로드맵의 진척도·우선순위가 같은 Facade 안에 혼재.
         "취직 준비 완료" 시 Axis만 archived하면 되지만,
         그 결과는 Facade 레벨에서 "완료" 신호가 없음.
         다음 커리어 방향 (PM 전환)을 추가하면 Axis가 계속 누적됨.

[다수 Facade 모델]
Facade A: "백엔드 개발자 취직"  [active]
Facade B: "사이드프로젝트 디자이너"  [active]

→ 각 Facade마다 독립된 목표, 진척도, 완료 신호.
   취직 완료 → Facade A archived.
   PM 전환 결심 → Facade C 신설.
```

### 5.3 Axis 다수 vs Facade 다수 — 표현력 비교

| 차원 | Axis 다수 (1 Facade) | Facade 다수 (N Facade) |
| --- | --- | --- |
| 독립 목표 | 축별로 있지만 Facade 레벨 목표는 1개 | Facade마다 독립 목표 |
| 진척 완료 신호 | Facade 완료 = 모든 Axis 완료? 정의 모호 | Facade 단위로 완료 선언 가능 |
| 전환/아카이브 | Axis 삭제 또는 정리 필요 | Facade 하나를 archived |
| 혼재 리스크 | 목적이 다른 학습 항목이 한 공간에 공존 | 목적별로 격리 |
| 현행 코드 변경 | 없음 | DB, API, FE 전반 변경 |

## 7. 권장 결정 — 판단 근거

### 권장: **(C) 하이브리드 (active=1 + archived=N)** — 단, v1.5 시점으로 연기

**즉시 권장 (v1 완료 후 첫 fix)**: **(A) 1개 유지** + FE `LF002` GET 폴백만 구현

**이유**:
1. "조합형 컨셉 로드맵"이 **목적 조합(B)**까지를 의미한다면 (B)가 맞지만, 구현 비용이 sdd 수준.
2. v1 현재는 M1 진행 중. (B) 결정은 도메인 모델·DB·API·FE 전반 변경 → M1 완료 후 별도 Epic 필요.
3. **(C) 하이브리드**는 (A)에서 가장 낮은 비용으로 "시간 조합(히스토리)"을 추가할 수 있다. 조합형 로드맵의 핵심인 "커리어 전환 이력 보존"을 지원.
4. (A)의 즉각 fix는 FE `LF002` GET 폴백 1건 → 현재 UX 장애 해소.

### 결정 트리

```
조합의 의미가 ...
│
├── "축(Axis) 수준 조합 — 한 컨셉 안에서 여러 학습 차원"
│     → (A) 유지. 현행 구조로 이미 지원. fix 불요.
│
├── "시간적 커리어 전환 + 이력 보존"
│     → (C) 하이브리드. pes 수준. M1 이후 v1.5.
│
└── "완전히 독립된 다수 커리어 정체성 동시 운영"
      → (B) 다수 허용. sdd 수준. M2 Epic.
```
