## [0.0.2v-01] V19 3-phase 무중단 마이그레이션  `[database · infra-deployment]`

**훅**: LearningAxis에 NOT NULL FK를 무중단으로 얹는 방법 — 단일 Flyway 안에 3-phase 순차 실행

**S (상황)**: `learning_layer` 신설 + `learning_axis.layer_id` FK 재배선 필요. prod DB에 이미 axis rows 존재. 무중단 배포 요구.
**T (과제)**: 컬럼 추가 · 백필 · NOT NULL 승격 · FK 등록 4단계를 순서·롤백 안전하게 실행.
**A (행동)**:
- Phase 1: `ALTER TABLE learning_axis ADD COLUMN learning_layer_id BIGINT NULL`
- Phase 2: `INSERT INTO learning_layer (...) SELECT ... WHERE NOT EXISTS (...)` — idempotent 백필로 Uncategorized Layer per facade 자동 발행 · `UPDATE learning_axis JOIN learning_layer ...` 로 axis id 매핑
- Phase 3: `ALTER TABLE learning_axis MODIFY COLUMN learning_layer_id BIGINT NOT NULL` + `ADD CONSTRAINT fk_learning_axis_layer FK`
- 세 phase가 단일 V19 안에 순차. R19 롤백 스크립트도 동일 순서로 준비.

**R (결과)**: 다운타임 0. FK violation 0. Flyway 정합성 유지. 이후 ADR021 axis-deck 통합 기반 마련.

**Trade-off**: 3단계 분리 → 마이그레이션 파일 복잡도↑ vs 단일 실행 안전성↑. 복잡도 감수.

**지표**: 3-phase 마이그레이션 소요 · 롤백 리허설 결과 (측정 시 기입)

**참조**: `docs/adr/ADR021-axis-deck-full-integration.md` · `src/main/resources/db/migration/V19__learning_axis_layer_fk.sql` · `.claude/rules/conventions.md` §3.8

## [0.0.2v-02] LearningAxis Soft Delete 승격 + 근본원인 추적  `[domain · database · observability]`

**훅**: "카드 만들 때 축 인식 실패 · 화면 이탈 시 사라짐" 이슈의 근본원인이 `orphanRemoval` hard delete임을 규명하고 Soft Delete로 승격

**S (상황)**: 사용자 report — 카드 생성 시 축 인식 실패 · 화면 이탈 시 데이터 사라짐. 원인 불명.
**T (과제)**: 근본원인 추적 + 재발 방지. axis는 원래 ADR003의 soft delete 대상 아님 (매핑성 엔티티로 분류됨).
**A (행동)**:
- `LearningFacade.removeAxis()`의 `orphanRemoval=true`가 hard delete를 유발 — 트랜잭션 중간에 컬렉션에서 빠지는 순간 DB에서 즉시 삭제. 재분류 결정.
- LearningAxis를 "사용자 자산" 카테고리로 재분류 (axis = deck 정책 강화).
- Flyway V14로 `deleted_at` 컬럼 추가 + `idx_learning_axis_deleted` + UNIQUE `(facade_id, name, deleted_at)` 3-col composite.
- 도메인 클래스에 `@SQLRestriction("deleted_at IS NULL")` + `softDelete()` + `isDeleted()`.
- `axes` OneToMany를 `orphanRemoval=false`로 낮춤 (회귀 트랩 차단).
- `LearningFacade`의 8개 지점(getAxes/findAxis/addAxis/validateAxisNameDuplicate/reorderAxes/isAxisCountExceedsRecommended/getCoverageSummary/hasUncoveredTopics)이 활성 축만 필터.
- Application Service가 `DeckCommandService.softDeleteByAxisId`로 소속 Deck 연쇄 처리.

**R (결과)**: 근본원인 원천 봉쇄. 활성 축 이름 재사용 허용 (softDeleted 이름 재사용). Deck 연쇄 소프트 삭제로 사용자 자산 보존.

**Trade-off**: ADR003 원칙 예외 발생 vs 사용자 자산 보존. ADR021로 명시 재승격.

**참조**: `docs/adr/ADR021-axis-deck-full-integration.md` · Flyway V14 · `fix-axis-deck-full-integration` 0.0.2v Story-set

## [0.0.2v-03] Deck 생성 진입점 유일화 (Axis 이벤트로만)  `[architecture · domain]`

**훅**: 사용자 명시 Deck 생성 경로를 전부 폐기하고 Axis 이벤트를 유일 진입점으로 → 축=덱 1:1 정책 강제

**S (상황)**: Deck 생성 경로가 여럿 (사용자 명시 POST, 자료 등록 시 자동, Axis 등록 시 자동) → 상태 불일치 · 동명 collision · 정책 흔들림.
**T (과제)**: Deck 생성 경로 단순화 · 축=덱 1:1 정책 강제 · legacy 흐름 정리.
**A (행동)**:
- Deck 팩토리 `Deck.createFromAxis(user, axisId, axisName)` **하나만** 남김. `Deck.of(...)`, `Deck.createUnderAxis(...)` 팩토리 폐기.
- 사용자 명시 진입점 (`POST /api/v1/decks`, `POST /learning-facade/axes/{axisId}/decks`) 폐기.
- `LearningAxisCreatedEvent`(immutable record, ADR007) → Deck BC 핸들러가 `existsByAxisIdAndDeletedFalse(axisId)` 멱등 체크 후 자동 생성.
- 자료 등록 시 Deck 자동 생성 흐름도 폐기 (Fix-Story 1~4).
- 응답 DTO에서 `deckCreated`/`deckId`/`deckName` 필드 제거.

**R (결과)**: Deck 생성 경로 = 이벤트 1개. axis=deck 1:1 계약 강제. 동명 collision 원천 소멸 (axis 이름이 이미 UNIQUE per facade).

**Trade-off**: 사용자 명시 생성 자유도 상실 vs 정책 일관성. 정책 일관성 우선.

**참조**: `docs/adr/ADR021-axis-deck-full-integration.md` · `LearningAxisCreatedEventHandler.java`

## [0.0.2v-04] AI 헥사고날 6-Port 확장 + Static/LLM Adapter 스왑  `[architecture · domain]`

**훅**: AI 제안 계층을 4-Port에서 6-Port로 확장 + `@ConditionalOnProperty`로 Static/LLM 무중단 교체 가능하게 설계

**S (상황)**: AI 제안 기능 초기 4-Port (Layer/Axis/Roadmap/Selections). LLM 도입 전이라 Static Adapter로 시작. 이후 Roadmap 아웃라인 · Selection 아웃라인 subtree까지 확장 필요.
**T (과제)**: 헥사고날 원칙 유지하면서 Port 확장 · Adapter 스왑 준비 · 테스트 stub 용이.
**A (행동)**:
- application/port/out/suggestion/ 하에 6개 Port interface (`LayerSuggestionPort`, `AxisSuggestionPort`, `RoadmapSuggestionPort`, `SelectionsSuggestionPort`, `ChaptersOutlineSuggestionPort`, `ChapterSubtreeSuggestionPort`, `SelectionOutlineSuggestionPort`, `SelectionSubtreeSuggestionPort`).
- infrastructure/suggestion/ 하에 각 Port에 대응하는 `Static{Name}Adapter`.
- `@ConditionalOnProperty(thirdtool.suggestion.provider=static, matchIfMissing=true)`로 default Static, 미래 `llm` 값 시 LLM Adapter 활성화.
- `RoleDetector` (concepts[] → role) + `SuggestionCatalog` (classpath JSON) + `SuggestionCatalogLoader` (lazy load + ConcurrentHashMap 캐시).
- Port 계약 테스트 (`SuggestionPortsContractTest` 15건).

**R (결과)**: LLM Adapter 미도입 상태에서도 API 응답 정상. 미래 property 하나로 무중단 교체. AI 호출 실패는 5xx 미노출 (ADR010).

**Trade-off**: Port 수 증가로 Adapter class 폭 증가 vs 확장 유연성. 유연성 우선.

**참조**: `docs/adr/ADR010.md` · `LearningFacade/application/port/out/suggestion/` · `StaticLayerSuggestionAdapter.java`

## [0.0.2v-05] LearningFacade.concepts[] 다중 컨셉 확장  `[domain]`

**훅**: 단일 String `concept` 컬럼을 1~5개 컬렉션으로 확장하면서 legacy 컬럼과 동기화 유지

**S (상황)**: 초기 `LearningFacade.concept: String` 단일 값. 사용자가 여러 컨셉 (예: "백엔드 개발자" + "인프라 학습")을 갖고 싶다는 요구.
**T (과제)**: 다중 값 확장 · 순서 관리 · legacy 컬럼 backward compat.
**A (행동)**:
- `learning_facade_concept` 테이블 신설 (Flyway V16) — displayOrder 1-based, UNIQUE(facade_id, concept_value).
- V17으로 기존 `concept` 값을 자식 테이블에 백필 (idempotent, NOT EXISTS 서브쿼리).
- `LearningFacade.concepts: List<LearningFacadeConcept>` 컬렉션 (`unmodifiableList`).
- 도메인 상수 `MIN_CONCEPT_COUNT=1`, `MAX_CONCEPT_COUNT=5`.
- `addConcept`, `removeConcept`, `updateConcept`, `updateConcepts(List)`, `reorderConcepts(orderedIds)` 도메인 메서드.
- 결과 VO: `ConceptChangeRecord` (단건), `ConceptsChangeRecord` (다건 · added/removed/kept · isChanged).
- legacy `concept` 컬럼은 유지 (첫 항목과 자동 동기화).

**R (결과)**: 다중 컨셉 지원. legacy 컬럼 backward compat. displayOrder 1-based로 유저 순서 관리.

**Trade-off**: legacy 컬럼 · 자식 테이블 이중 표현 (일관성 유지 부담) vs 안전한 이관. 이관 안전성 우선.

**참조**: Flyway V16, V17 · `LearningFacade.java` · `ConceptsChangeRecord.java` · Story-LT-E1

## [0.0.2v-06] LearningLayer 그룹핑 계층 도입 + default Uncategorized 앵커  `[domain · database]`

**훅**: Axis 상위에 Layer 그룹핑 도입하고 default "Uncategorized" Layer를 삭제 금지 앵커로 자동 발행

**S (상황)**: Axis 목록이 많아질 때 그룹핑 필요. 신규 Facade 생성 시에도 자연스러운 진입점 필요. 백필 시 legacy axis들의 소속 결정 필요.
**T (과제)**: Layer 도입 + 자동 라우팅 + 신규 사용자 진입점 + 백필 정합성.
**A (행동)**:
- `learning_layer` 테이블 신설 (Flyway V18) — softDelete + composite UNIQUE `(facade_id, name, deleted_at)`.
- `LearningFacade.create()` 시 자동 Uncategorized Layer 발행.
- default Layer는 삭제 금지 (자동 라우팅 앵커).
- `LearningLayer.softDelete()`는 활성 axis 존재 시 `LEARNING_LAYER_HAS_ACTIVE_AXES` 409 (cascade 금지, 사용자 명시 요구).
- V19의 3-phase 이관으로 기존 axis들을 facade별 Uncategorized로 자동 매핑.
- `@SQLRestriction` + `@SQLDelete` (Hibernate 관행 · Repository 명시 필터 코드 감소).

**R (결과)**: Axis 그룹핑 UX. 신규 Facade의 addAxis(name) legacy 경로가 default Layer로 자동 라우팅. 백필 데이터 정합 유지.

**Trade-off**: default Layer 자동 발행 → 유저가 유일 Layer 갖고 시작 (UI 노출 여부 별도 결정) vs 초기 상태 안정 보장.

**참조**: Flyway V18 · V19 · `LearningLayer.java` · Story-LT-E2 · ADR021

## [0.0.2v-07] Deck↔Axis 가시화 결정 (도메인 승격 거부)  `[api-contract · domain]`

**훅**: axisName을 응답에 노출하되 도메인 연관 승격은 거부하고 read-model 노출로 한정

**S (상황)**: 프론트에서 Deck 응답에 axisName 필요. Option A) `Deck.axis: LearningAxis` 도메인 필드 추가 · Option B) `DeckQueryService`가 axisId 배치로 axisName 조회 후 read-model에 얹기.
**T (과제)**: BC 간 도메인 참조 최소화 원칙(FK id만) 유지하면서 사용자 UX 요구 충족.
**A (행동)**:
- **Option B 채택**. Option A는 거부.
- `DeckResponse.Summary/Detail`에 `axisId`/`axisName` 필드.
- `DeckQueryService`가 결과 조합 시 `LearningFacadeQueryService.findAxisNamesByIds(...)`로 배치 조회 (N+1 회피).
- QueryDSL 검색 경로 (`DeckSummaryRow`)는 raw axisId만 투영, 후처리 조합.
- Deck 도메인 클래스는 `axisId: Long`만 소유 (변경 없음).

**R (결과)**: BC 격리 유지. 프론트 UX 요구 충족. N+1 없음.

**Trade-off**: `DeckQueryService`에 조합 로직 추가 vs 도메인 모델 오염 방지. 도메인 순수성 우선.

## [0.0.2v-09] BC 간 협력 = 동기 도메인 이벤트 정착  `[architecture · collaboration]`

**훅**: `@Async` · `@TransactionalEventListener` 유혹 거부하고 `@EventListener` 동기 처리로 원자성·단순함 확보

**S (상황)**: Axis 등록 시 Deck 자동 생성 · Material 삭제 시 Deck 참조 해제. BC 간 협력 방식 결정 필요.
**T (과제)**: BC 격리 유지 + 트랜잭션 원자성 + 재시도·순서 복잡도 회피.
**A (행동)**:
- immutable record 이벤트 (`LearningAxisCreatedEvent`, `LearningMaterialDeletedEvent`).
- `ApplicationEventPublisher.publishEvent(...)` 발행자 트랜잭션 안에서.
- Deck BC 핸들러 `@EventListener` 동기 수신. `@Async` 금지, `@TransactionalEventListener` 금지.
- 핸들러 실패 시 발행자 트랜잭션 롤백.
- 멱등 보장 (`existsByAxisIdAndDeletedFalse`, `Deck.markMaterialDeleted()` no-op).
- `LearningMaterialDeletedEvent`는 physical delete **직전** 발행 (FK 안전).

**R (결과)**: 재시도·순서·부분실패 복잡도 회피. BC 격리 유지. 트랜잭션 원자성 확보.

**Trade-off**: 이벤트 처리가 발행자 성능에 영향 vs 원자성 · 단순함. 초기 규모엔 후자 우선.

**참조**: `docs/adr/ADR007.md` · `LearningAxisCreatedEventHandler.java` · `LearningMaterialDeletedEventHandler.java`

## [0.0.2v-10] 결과 VO 패턴 · 다건 통째 교체 패턴  `[domain · api-contract]`

**훅**: 상태 변경 결과를 `ChangeRecord` VO로 반환해 Application Service가 저장 여부 결정하도록 캡슐화

**S (상황)**: `updateConcept` · `updateConcepts` 같은 다건 변경 API. 실제 변경 여부·added/removed 계산·저장 skip 최적화 필요.
**T (과제)**: 도메인이 변경 여부·상세 알림, Application Service가 판단.
**A (행동)**:
- `ConceptChangeRecord`, `ConceptsChangeRecord` 등 VO 도입.
- 필드: `previous`, `current`, `added`, `removed`, `kept`, `isChanged()`.
- 정적 팩토리 `changed(...)`, `unchanged(...)`로만 생성.
- 다건 통째 교체 (`updateConcepts(List)`) — 트랜잭션 내 clear + rebuild, orphanRemoval로 detach 자식 자동 삭제, 부분성공 불허.
- `isChanged() == false`면 Application Service는 저장 쿼리 생략 (updatedAt 갱신 없음).

**R (결과)**: 무의미한 UPDATE 방지. added/removed 계산 명확. 부분 성공 방지.

**Trade-off**: VO 추가로 도메인 코드 늘어남 vs 명시성 · 최적화. 명시성 우선.

**참조**: `.claude/rules/conventions.md` §1.10 · `LearningFacade.updateConcepts()` · `ConceptsChangeRecord.java`
