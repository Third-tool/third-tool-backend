# [Fix · SDD] 양식 정의 (풀버전)

> **fix 트랙**: 원본 SDD 명세의 **부분 폐기·재작성 / Product 단위 아키텍처 결정 번복** 트래킹 문서.
> planning은 `../../../../pes/sdd/version/0.0.1v/sdd.md`(시간 기반 1~2개월 도메인 재설계) 참조.
> fix는 **수정 범위·복잡도** 기준 5단계 중 최대 단위 — 원본 명세를 의미 있게 바꿔 새 결정 흐름을 정착.

---

## 사용 시점 (트리거)

다음 조건 중 **3개 이상**을 만족할 때 본 양식을 쓴다.

- [ ] 원본 SDD의 **설계 결정(Design Decisions) 1+개가 번복** 또는 폐기됨
- [ ] 컴포넌트 배치·핵심 플로우가 의미 있게 재구성됨
- [ ] 마이그레이션 단계(Product 의존성 / 환경별 설정 / Epic·Story 의존성 그래프)가 갱신
- [ ] 실패 모드 / 로깅 정책 / 관측 지표 매트릭스가 갱신
- [ ] 거부된 원안과 새 선택 사이의 트레이드오프를 새로 기록해야 함
- [ ] 원본 KPI / Scope가 변경

**졸업 신호 → 완료·통합**:
- 본 fix가 충분히 안정되면 원본 SDD의 해당 섹션을 직접 갱신하고 본 fix는 archive
- 또는 새 SDD 버전(`../0.0.2v/sdd.md`)으로 통합 후 본 fix는 reference로 남김

### 섹션 가이드

| 섹션 | 핵심 |
| --- | --- |
| **메타 (§0)** | 원본 SDD 정확히 식별. Product 번호 + 영향 Epic/Story 모두 |
| **배경 (§1)** | 원본이 선택했던 흐름·문제·타이밍 3축 |
| **폐기 원안 (§3)** | 원본의 합리적 근거를 인정하면서 폐기. "원안이 틀렸다"는 톤 X — "외부 조건이 변했다"는 톤 |
| **새 결정 (§4)** | 거부된 후보 비교가 다시 필요하면 Option A/B/C로 |
| **마이그레이션 (§8)** | 단계 순서가 실행 가능해야 함. "동시에 다 바뀜" 금지 |
| **검증 (§10)** | 통합 테스트 + 배포 계획 + 롤백 절차 (3축) |
| **영향 (§11)** | 원본 SDD에 [명세 변경 이력] 추가 + ADR 신규 + 후속 fix 발행 ownership |
| **자가 점검 (§13)** | fix/sdd는 보통 ADR 발행을 동반함. 미발행이면 §13에서 catch |

## 예시

본 양식의 첫 운영 사례는 향후 발생 시 본 디렉토리에 사례 .md로 누적. 일반적 사례 패턴:

- 원본 SDD의 "Option A 선택"이 운영 6개월 후 실패 신호 누적으로 폐기 → Option B 또는 신규 Option D로 전환
- 외부 인프라(예: AWS RDS → Aurora) 변경으로 Product 마이그레이션 단계 재설계
- 외부 LLM Provider 변경으로 AI Suggestion Product Out-of-Process 의존 재구성

각 사례는 본 양식의 모든 섹션(0~13)을 풀로 채우는 것이 원칙. 큰 결정 번복의 트레이드오프를 가볍게 다루면 다음 fix가 같은 자리를 또 한 번 번복하게 된다.
