# ADR007: BC 간 협력에 동기 도메인 이벤트를 도입한다

- **상태**: Accepted (2026-05-14) → **Amended (2026-06-30)** — Fix: 트리거 Material → Axis 이전
- **날짜**: 2026-05-14 (최초), 2026-06-30 (수정)
- **관련**: [ADR005](ADR005.md), `docs/PACKAGE.md` §6 BC 간 의존 규칙
- **수정 근거**: `workflow/task/fix/pes/version/0.0.1v/fix-axis-deck-refactor.md` (Axis = 학습 실행 공간 단위, Deck은 Axis와 1:1)

## 2026-06-30 수정 요약 (Fix-Story 1~4)

본 ADR이 채택한 "동기 도메인 이벤트 + `@EventListener`" 패턴 자체는 그대로 유지한다. **변경된 것은 트리거 지점뿐**이다.

| 항목 | Before | After |
| --- | --- | --- |
| Deck 자동 생성 트리거 | `LearningMaterialCommandService.createMaterial` | `LearningFacadeCommandService.addAxis` |
| 발행 이벤트 | `LearningMaterialCreatedEvent` (mutable, `setResult` 채널) | `LearningAxisCreatedEvent` (immutable record) |
| 핸들러 | `Deck/application/event/LearningMaterialCreatedEventHandler` | `Deck/application/event/LearningAxisCreatedEventHandler` |
| Deck 정적 팩토리 | `Deck.createFromLearningMaterial(user, axisId, materialId, name)` | `Deck.createFromAxis(user, axisId, name)` |
| Deck ↔ Material 관계 | 자료 1건 = Deck 1개 | 무관 (Material은 Deck과 직접 매핑 없음. axis_id로만 연결) |
| 결과 통신 채널 (`setResult`) | 응답에 `deckId`, `deckName` 포함 | **삭제** — 자료 등록 응답에서 Deck 필드 제거 (Axis 등록 흐름이 책임짐) |
| 멱등성 | 동명 Deck 발생 시 `DECK_NAME_DUPLICATE` 예외 | 핸들러가 `existsByAxisIdAndDeletedFalse` 선체크 → 이미 존재 시 no-op |

**남는 ADR007 본질**: BC 간 단방향 의존 + 같은 트랜잭션 안 동기 실행 + 핸들러가 throw하면 호출자 트랜잭션 롤백.

**폐기된 결정 항목**: mutable 이벤트 + `setResult` 결과 통신 채널. Axis 트리거는 호출자가 응답에 Deck 정보를 요구하지 않으므로 immutable record로 단순화됐다.

## 컨텍스트 (원본)

Story-005-1 — 학습 자료(`LearningMaterial`) 등록 시 동명의 `Deck`이 자동 생성되어 축에 귀속되어야 한다 (Epic 5). LearningFacade BC가 Deck BC와 처음으로 협력하는 흐름이며, 다음 두 제약이 동시에 걸린다.

1. **동기 트랜잭션 보장 필요** — Story 본문이 "동명 Deck 존재 시 확인 팝업"을 요구한다. 자료 등록 응답에 `409 + DECK_NAME_DUPLICATE`를 즉시 반환해야 하며, 자료 저장도 같은 트랜잭션에서 롤백되어야 한다.
2. **BC 결합도 최소화** — 기존 BC 협력은 `Card → Deck`, `Review → Card·Deck`처럼 Application Service에서 Repository/QueryService를 직접 주입하는 패턴이었다. 그러나 Epic 5 메모는 "이벤트 기반 단방향 연동"을 명시했고, 자료 등록 흐름이 Deck 생성을 "요청"하는 의도(자료가 Deck 생성의 진입점)를 명확히 표현하고 싶다.

여기서 일반적 도메인 이벤트 패턴(`@TransactionalEventListener(AFTER_COMMIT)`)은 두 번째 요구만 만족시킨다 — 비동기 처리라 자료 응답에 동명 충돌 결과를 줄 수 없다.

또 부차적으로, 자료 등록 응답이 생성된 Deck의 `deckId`/`deckName`을 포함해야 한다 (FE가 "Deck으로 이동" 버튼에 사용). 비동기 이벤트로는 호출자가 결과를 받을 채널이 없다.

### 컨텍스트 (2026-06-30 수정 — 트리거 재배치 근거)

본 fix는 위 컨텍스트의 두 번째 항목을 재해석한다. `issue2b-facade-multicontext-deck-arc-report.md` §5에서 다음이 확인됐다:

- **Axis = 학습 실행 공간 단위**. 사용자는 1개 Facade 안에 여러 Axis(목표)를 두고, 각 Axis 안에서 Topic을 다뤄가며 Deck 학습을 진행한다.
- 따라서 **Deck은 Material 단위가 아니라 Axis 단위로 자동 생성**되어야 한다. Material은 Axis-Topic 커버리지 보강의 입력 자료일 뿐, Deck 생성의 진입점이 아니다.
- 자료 등록 응답에 `deckId`/`deckName`을 포함시켜 "Deck으로 이동"을 유도했던 FE 흐름은 사용자가 Axis 단위로 학습 공간을 이동하도록 다시 설계된다.

이로 인해 ADR007 원본 결정의 두 가지 핵심 — (a) Material 등록을 진입점으로 본 점, (b) 응답에 Deck 결과를 동기 통신한 점 — 이 모두 무효화된다.

## 결정

**Spring `@EventListener` 동기 도메인 이벤트**로 BC 협력을 구현한다.

- 이벤트는 발행 BC(`LearningFacade/domain/event/LearningAxisCreatedEvent`)에 정의한다. 수신 BC(Deck)가 import한다 — 단방향 의존 `Deck → LearningFacade`.
- 핸들러는 수신 BC의 application 계층에 둔다 (`Deck/application/event/LearningAxisCreatedEventHandler`).
- `@TransactionalEventListener`가 **아닌** `@EventListener`를 사용해 호출자(`LearningFacadeCommandService.addAxis`) 트랜잭션 안에서 동기 실행한다. 핸들러가 throw하면 Axis 추가 트랜잭션 전체가 롤백된다.
- **이벤트 객체는 immutable record**. 핸들러는 결과를 호출자에 통신하지 않는다 (Axis 등록 응답에는 Deck 정보가 포함되지 않는다 — FE는 별도 조회로 가져온다).
- **핸들러는 멱등** — `DeckRepository.existsByAxisIdAndDeletedFalse(axisId)`로 같은 axis에 활성 Deck이 이미 있으면 no-op로 종료. 이벤트 재발행·재시도 시에도 중복 생성되지 않는다.

### 폐기된 결정 (2026-06-30)

- ~~mutable 일반 class 이벤트 + `setResult(deckId, deckName)` 결과 통신~~ — Axis 트리거에서는 호출자가 결과를 요구하지 않으므로 표준 immutable record로 복귀.
- ~~동명 Deck 검사 → `DECK_NAME_DUPLICATE` 예외~~ — Axis 단위 멱등성 검사(`existsByAxisIdAndDeletedFalse`)로 대체. 사용자 충돌 확인 팝업 흐름은 본 fix 범위에서 제거된다.

## 결과 (Consequences)

**긍정적**

- BC 간 협력 의도가 코드 레벨에서 명시적으로 분리된다 — Axis 추가 Service는 "이벤트 발행"만 알면 되고, Deck 생성 세부 로직(이름 결정·멱등 검사)은 Deck BC 안에 응집된다.
- 같은 트랜잭션이라 원자성 보장 — Axis 저장 후 Deck 저장 실패 시 Axis도 함께 롤백.
- 이벤트가 immutable record로 단순화되어 일반 도메인 이벤트 표준과 일치 (2026-06-30 수정).
- 핸들러 멱등성으로 재시도·이벤트 중복 발행에 안전 (2026-06-30 수정).

**트레이드오프 / 부정적**

- **새 BC 의존 도입** — Deck → LearningFacade (이벤트 import). `docs/PACKAGE.md` §6에 새 행 추가 필요.
- **Spring 이벤트 인프라 도입** — 코드베이스 첫 사례. 다른 BC 협력 패턴(직접 주입)과 다른 모델이 공존.
- ~~이벤트 객체가 mutable~~ — 2026-06-30 수정으로 immutable record화. 해당 항목 폐기.
- ~~핸들러가 throw하는 동명 충돌 예외가 BC 경계 두 번 가로지름~~ — 2026-06-30 수정으로 멱등 처리. 해당 시나리오 자체가 사라짐.

## 대안 비교

| 대안 | 장점 | 거부 사유 |
| --- | --- | --- |
| 직접 주입 (`DeckCommandService` 또는 `DeckQueryService` 주입) | 기존 BC 협력 패턴과 일관. 결과 통신 자연스러움 | Epic 5 메모의 "이벤트 기반 단방향" 의도와 어긋남. BC 협력 의도가 코드에 덜 명시적 |
| `@TransactionalEventListener(AFTER_COMMIT)` 비동기 이벤트 | 일반 도메인 이벤트 표준 | (원본) 자료 응답에 409를 줄 수 없음. (2026-06-30) Axis 트리거에서는 응답 결합 요구가 사라져 재검토 가치 있음 — 다만 본 fix는 범위 한정으로 동기 패턴 유지 |
| Coordinator Service 신설 (`AxisDeckCoordinator`) | 양쪽 BC의 협력 의도를 한 객체에 응집 | 새 추상화 도입. BC 둘 다 알아야 해 결합도 더 높음. 본 fix 한정으로 무게 과함 |

## 다시 검토할 시점

- **BC 협력이 3개 이상 본 패턴(`@EventListener` 동기 + immutable record)을 따르게 된 시점** — 패턴이 표준화되었음을 의미. 가이드라인 문서(`docs/PACKAGE.md` BC 협력 섹션)에 정착시킨다.
- **비동기 처리 요구가 발생한 시점** (예: Axis 추가 후 외부 API 호출, 메일 발송 등) — `@TransactionalEventListener(AFTER_COMMIT)`로 옮길 수 있다. immutable record는 비동기 전환에도 안전.
- **BC 의존 그래프가 복잡해져 사이클 위험이 보이는 시점** — Deck → LearningFacade 의존이 다른 BC와 결합되어 양방향이 되지 않는지 점검한다.
- **Axis 1개 = Deck 1개 가정이 깨지는 시점** — 예: 같은 Axis에 여러 Deck을 두는 요구. 핸들러 멱등성 검사 로직(`existsByAxisIdAndDeletedFalse`)이 더 이상 의미를 가지지 않으므로 별도 ADR 필요.

## Backfill 결정 (2026-06-30)

본 fix 시점의 prod DB는 **그린필드** — 1차 배포 직전 단계이며, Deck 없이 등록된 Axis가 존재할 가능성이 없다 (Story-051에서 RDS 단일-AZ 초기 셋업 완료, 사용자 데이터 0건). 따라서 backfill Flyway migration을 본 fix에 포함하지 않는다.

만약 운영 진입 후 본 fix를 적용할 경우, 다음 backfill 스크립트가 필요하다:

```sql
-- 가상의 V14__backfill_deck_per_axis.sql (현 시점 미적용)
INSERT INTO deck (name, user_id, axis_id, learning_material_id, depth, mode,
                  progress_status, on_library, deleted, created_date, updated_date,
                  last_accessed)
SELECT la.name, lf.user_id, la.id, NULL, 0, 'ON_FIELD',
       'NOT_STARTED', false, false, NOW(6), NOW(6), NOW(6)
FROM learning_axis la
JOIN learning_facade lf ON lf.id = la.facade_id
LEFT JOIN deck d ON d.axis_id = la.id AND d.deleted = false
WHERE d.id IS NULL;
```

운영 데이터가 발생한 이후 본 fix 패턴을 다른 환경에 도입할 때 위 스크립트를 작성·검증해 적용한다.
