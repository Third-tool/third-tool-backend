# ADR008: 로깅 인프라 — profile별 Appender 분기와 LogstashEncoder를 채택한다

- **상태**: Accepted
- **날짜**: 2026-05-17
- **관련**: Product 0 Epic 1 (JSON 구조화 로그 포맷), Story-001-1, `.claude/rules/conventions.md` §2 (API/Exception), `docs/PACKAGE.md` Common·infra 경계

## 컨텍스트

ThirdTool은 본 결정 시점까지 Spring Boot 기본 로깅 설정만 사용해왔다. 환경별 분기가 없고, `application.yml`에 공통 `logging.level` 블록 하나만 두는 상태였다. 다음 세 가지 제약이 동시에 걸린다.

1. **수집기 호환성** — 향후 로그 수집기(Loki / CloudWatch Logs / OpenSearch 등)를 붙일 때 평문 상태에서는 전체 포맷 마이그레이션이 필요하다. JSON으로 미리 표준화해두면 마이그레이션 비용이 없다.
2. **개발자 가독성 유지** — 로컬 개발 중에는 사람이 눈으로 빠르게 읽어야 하므로 컬러 평문이 효율적이다. JSON은 콘솔에서 직접 읽기 어렵다.
3. **MDC 필드 누수 방지** — 후속 Epic 2에서 `requestId`·`userId` 같은 컨텍스트 필드를 MDC로 전파할 예정이지만, 화이트리스트 없이 LogstashEncoder를 쓰면 임의 키(`MDC.put("foo","bar")`)가 모두 JSON에 노출되어 PII 유출 사고 위험이 있다.

또한 현 `application.yml`에 `org.hibernate.orm.jdbc.bind: TRACE`가 공통 설정으로 들어가 있어, 머지 후 prod에서 쿼리 파라미터(개인정보 포함)가 그대로 로그에 노출될 위험이 잠재해 있다.

## 결정

**3축 결합 결정**으로 본 ADR에 합본한다 — 셋이 동시에 만족되어야 위 세 제약이 모두 풀린다.

### 1. profile별 Appender 분기를 `logback-spring.xml` 한 파일의 `<springProfile>` 태그로 처리

별도 설정 파일 분리(`logback-spring-prod.xml`)는 환경 간 drift 위험이 커서 채택하지 않는다. 한 파일 안에서 `<springProfile name="local">` / `<springProfile name="dev,prod">`로 분기한다.

- `local` → `CONSOLE_PLAIN` Appender, 컬러·`%logger{36}` 패턴, UTF-8
- `dev,prod` → `CONSOLE_JSON` Appender, `LogstashEncoder`
- logger별 레벨은 같은 파일의 `<springProfile name="dev"|"prod">` 블록에 명시. `application.yml`의 공통 `logging.level.*` 블록은 제거해 단일 진실 소스 확보.

### 2. JSON 인코더는 `net.logstash.logback:logstash-logback-encoder:8.0`

Spring Boot 3.5.5 BOM과 충돌 없이 해석된다(`runtimeClasspath` 확인). Logback ConsoleAppender의 encoder로 그대로 꽂는다.

```xml
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <customFields>{"application":"thirdtool"}</customFields>
    <includeMdcKeyName>traceId</includeMdcKeyName>
    <includeMdcKeyName>requestId</includeMdcKeyName>
    <includeMdcKeyName>userId</includeMdcKeyName>
    <includeMdcKeyName>method</includeMdcKeyName>
    <includeMdcKeyName>path</includeMdcKeyName>
    <includeContext>false</includeContext>
</encoder>
```

표준 JSON 필드: `@timestamp · level · logger_name · thread_name · message · application · stack_trace`. 멀티라인 예외는 LogstashEncoder가 자동으로 `\n` 이스케이프해 한 라인 안에 직렬화한다.

### 3. MDC 화이트리스트로 노출 필드를 명시한다

`includeMdcKeyName`을 화이트리스트로 사용한다(블랙리스트 아님). 화이트리스트는 다음 5개로 한정:

| 키 | 의미 |
| --- | --- |
| `traceId` | OpenTelemetry Semantic Conventions 호환 (분산 트레이스 도입 대비) |
| `requestId` | HTTP 요청 단위 식별자 (Epic 2에서 필터로 주입 예정) |
| `userId` | 인증된 사용자 식별자 (Epic 2) |
| `method` | HTTP 메서드 |
| `path` | 요청 경로 |

이 외에 코드가 임의로 `MDC.put`한 키는 JSON에 노출되지 않는다 (회귀 방지: `LogbackJsonFormatTest`에서 검증).

### prod 부속 결정 — `hibernate.orm.jdbc.bind`를 OFF

prod 섹션의 `<springProfile name="prod">` 블록에서 `org.hibernate.SQL=OFF`, `org.hibernate.orm.jdbc.bind=OFF`로 강제한다. 쿼리 바인딩 파라미터를 통한 PII 유출 위험을 차단.

## 결과 (Consequences)

### 긍정적

- 수집기 도입 시점에 포맷 마이그레이션이 불필요하다. 필드 귀속(`logger_name` vs `loggerName` 등) 정합성만 점검하면 그대로 흘려보낼 수 있다.
- MDC 화이트리스트로 의도치 않은 컨텍스트 필드 노출이 차단된다. 화이트리스트 키를 추가하려면 본 ADR을 수정해야 하므로 의사결정이 추적된다.
- `hibernate.orm.jdbc.bind: TRACE`에 의한 PII 노출 잠재 위험이 prod에서 코드 레벨로 차단된다.
- 개발자가 `application.yml`을 만지지 않고도 `--spring.profiles.active=...`만으로 로그 포맷을 전환할 수 있다.

### 트레이드오프 / 부정적

- 평문 대비 로그 라인 길이가 약 1.5~2배 증가한다 (JSON 키 오버헤드). dev/prod 디스크·전송 비용 미세 증가.
- 컬러 출력은 local 한정. 다른 환경 콘솔(EC2 stdout 등)에선 색 정보 없음.
- 새 MDC 키를 추가하려면 ADR 수정 + `logback-spring.xml` 갱신이 필요하다. 화이트리스트의 운영 비용.
- 통합 테스트(`LogbackJsonFormatTest`)가 Spring Boot 내부 클래스(`LogbackLoggingSystem`)에 의존한다. Spring Boot 메이저 업그레이드 시 API 변경 위험.
- CI(`dev-cicd.yml`)는 `-x test`로 테스트를 스킵하므로 본 회귀 방지 테스트가 CI에서 실행되지 않는다. 로컬·로컬 PR 단계에서만 검증 가능.

## 대안 비교

| 대안 | 장점 | 거부 사유 |
| --- | --- | --- |
| 별도 설정 파일 분리 (`logback-prod.xml` / `logback-local.xml`) | 환경별 의도 명확 | 파일 간 drift 위험. 공통 정책(`hibernate=OFF` 등)이 한 곳에 모이지 않음 |
| 수집기 측에서 평문 → JSON 변환 (Filebeat parser) | 애플리케이션은 평문 유지 | 수집기 변경(Loki → OpenSearch 등) 시 파서 재작성. 다중 라인 예외 파싱이 불안정 |
| Custom JsonLayout 직접 구현 | 필드 완전 제어 | 직접 유지보수 부담. `LogstashEncoder`가 이미 표준 필드 + MDC 지원을 제공 |
| `customFields`/MDC 화이트리스트 없는 LogstashEncoder | 단순 | 임의 MDC 키 노출. `application` 같은 식별자가 빠져 다중 서비스 환경에서 구분 불가 |
| 환경변수만으로 분기 (예: `LOG_FORMAT=json`) | 코드 한 줄로 토글 | Logback 동적 분기를 직접 구현해야 함. `<springProfile>`이 더 깔끔 |

## 다시 검토할 시점

- **외부 수집기(CloudWatch Logs / Loki / OpenSearch) 도입 시점** — 필드명 귀속(`logger_name` vs `loggerName`, `@timestamp` vs `timestamp` 등) 정합성 점검. 수집기가 평문 가정으로 파싱 중이면 마이그레이션 절차 별도 ADR.
- **멀티 인스턴스/멀티 리전 배포 시점** — 인스턴스 ID, region, hostname 필드 추가 검토. `customFields`만 늘려도 호환.
- **`AsyncAppender` 도입 검토 시점** — 본 ADR은 동기 ConsoleAppender만 사용. 부하 테스트 후 GC pause / 백프레셔 트레이드오프 측정해 별도 ADR.
- **MDC 화이트리스트가 7개 이상으로 확장되는 시점** — PII/카디널리티 정책(예: `email`, `phone` 같은 직접 식별자 금지) 별도 ADR.
- **Spring Boot 메이저 업그레이드(4.x 등) 시점** — `LogbackLoggingSystem` API 호환성 회귀 점검. 깨지면 테스트 패턴 재구성.
