# ADR012: 운영 컨테이너 base image를 `eclipse-temurin:21-jre-alpine`로 채택하고 Distroless 도입은 보류한다

- **상태**: Accepted
- **날짜**: 2026-06-25
- **관련**: Product 5 컨테이너 배포 Epic 1, Story 1-1 (Dockerfile 통합), `docs/operations/troubleshooting/ts005-dockerfile-build.md`, `workflow/task/pes/sdd/product-infra-deploy.md`

## 컨텍스트

Story 1-1로 운영 Spring Boot 서버 컨테이너 이미지 빌드 표준을 통합한다. spec(`product-infra-deploy.md` 라인 697-703)은 **`gcr.io/distroless/java21-debian12:nonroot`** (Distroless) base image를 권고한다. 반면 기존 `Dockerfile-dev`는 **`eclipse-temurin:21-jdk-alpine`** (Alpine + 풀 JDK)를 사용하고 있어 런타임 이미지 비대(~250MB) + JDK 도구가 runtime에 불필요한 상태.

두 선택지 모두 200MB 미만 목표(milestone Tier 1 #9 한 줄 AC)를 달성한다. 차이는 운영 디버깅 비용·보안 표면·빌드 부담의 trade-off.

## 결정

**`eclipse-temurin:21-jre-alpine`을 채택**하고 Distroless 도입은 **운영 안정화 이후 별도 Story**로 위임한다.

### Dockerfile 구성

```
# Stage 1 (builder):   gradle:8.8-jdk21-alpine — Spring Boot bootJar
# Stage 2 (extractor): eclipse-temurin:21-jre-alpine + jarmode=tools extract --layers
# Stage 3 (runtime):   eclipse-temurin:21-jre-alpine + 비-root user + Asia/Seoul + layer COPY
```

runtime base 이미지의 핵심 결정:
- **JRE만 사용** (JDK 도구 제거) → 약 100MB 절감, 최종 이미지 ~150MB
- **Alpine 베이스** (musl libc) — Debian 기반 대비 더 경량, Spring Boot fat jar는 musl 호환
- **비-root user `app`** + Asia/Seoul timezone — 보안 baseline + 기존 동작 보존

## 결과 (Consequences)

### 긍정적

- **운영 디버깅 용이성**: shell·package manager 보유. 컨테이너 부팅 실패·메트릭 이상 시 `docker exec`으로 진입해 환경변수·파일·DNS 직접 점검 가능. 1인 운영 단계에서 critical.
- **마이그레이션 비용 최소**: 기존 Dockerfile-dev가 동일 family(`eclipse-temurin`). team familiarity가 보존됨.
- **tzdata 등 표준 패키지 즉시 사용 가능** — Asia/Seoul 설정 1줄, JVM agent(`-javaagent:`) 정상 동작.
- **이미지 < 200MB 목표 동등 달성** (~150MB).
- **Spring Boot 3.x `jarmode=tools`로 layered jar 활용** — deps 변경 없으면 application layer만 재빌드.

### 트레이드오프 / 부정적

- **공격 표면 다소 큼**: shell·apk 등 컨테이너 내부 실행 가능. 위협 모델은 "이미지 자체 유출"이 아닌 "이미지 내부 코드 실행" — 후자는 ALB 내부망 차단·IAM Role 최소 권한·비-root user로 보완.
- **Alpine musl libc 일부 native 라이브러리 비호환** — 본 프로젝트 의존성(Spring Boot 3.5 + Hikari + Flyway + MySQL driver + Lombok + JJWT)은 모두 musl 호환. 향후 native lib 도입 시 재평가.
- **Distroless 대비 layer 수 약간 많음** (apk·user 생성) — layered jar 캐시로 보완.

## 대안 비교

| 대안 | 장점 | 거부 사유 |
| --- | --- | --- |
| `gcr.io/distroless/java21-debian12:nonroot` (spec 권고) | 공격 표면 최소, ~120MB, 비-root 기본 | shell·package manager 부재로 운영 디버깅 어려움 / tzdata 추가 비용 / `-javaagent:` JVM agent 미지원 |
| `eclipse-temurin:21-jdk-alpine` (기존) | 친숙, JDK 도구로 디버깅 풍부 | runtime에 javac·jar·jstack 등 불필요 → 이미지 250MB로 비대, AC `< 200MB` 위반 |
| `eclipse-temurin:21-jre-jammy` (Ubuntu) | Debian 기반, glibc 표준 | ~200MB로 AC 경계, Alpine 대비 50MB 무거움, OS 패치 surface 큼 |
| `amazoncorretto:21-alpine` (AWS) | AWS 최적화, ~160MB | AWS lock-in (멀티 클라우드 차단), community 작음 |
| `openjdk:21-slim` (Debian slim) | 공식 OpenJDK, ~180MB | 보안 패치 빈도 낮음, Eclipse Temurin이 더 적극적인 LTS 패치 |

## 알려진 follow-up (본 ADR 범위 외)

- **Distroless 전환 재평가** — 운영 안정화 후. 다음 신호 충족 시 Story 신설:
  - 운영자가 6개월간 `docker exec` 디버깅을 거의 사용하지 않음
  - 컨테이너 부팅 실패가 환경변수·secret 누락(외부 진단 가능) 외 사유가 없음
  - JVM agent(APM) 도입 계획이 없거나 distroless-debug 이미지로 분리 가능
- **`-javaagent:` 도입 시 검토** — Datadog APM, OpenTelemetry Java Agent 등. Distroless 미지원, eclipse-temurin 정상.
- **uid/gid 명시 부여** — 현재 자동 할당. ECS Task Definition `user` 필드 또는 EFS volume mount 시 fix uid 권장 (Distroless `nonroot` 관례 65532 또는 임의 10001).
- **GraalVM native image** — v2 startup·메모리 최적화. base image 자체가 재정의.
- **`Dockerfile-elasticsearch` base image 정책** — 별도 ECR repository로 분리. 본 ADR 범위 외.

## 다시 검토할 시점

- **Distroless 전환 결정 시점** — 운영 안정화 + APM 도입 결정 + 보안 감사 후
- **musl 비호환 의존성 도입 시점** — `eclipse-temurin:21-jre-jammy` (Ubuntu) 전환 검토
- **GraalVM AOT 도입 시점** — base image 재정의
- **이미지 크기가 200MB를 초과하는 시점** — 의존성 audit + base image 재평가
