## 1. Context — 왜 이 인계가 필요한가

본주(M1) 백엔드는 `milestone.md`(D1~D6)에 따라 19 Story를 한 주에 처리한다. 19개 중 **FE에 직접 영향이 있는 변경**은 소수지만 본주에 **첫 dev 배포**가 발생한다는 사실이 인계의 트리거다. dev 환경에 BE/FE가 처음 한 호스트에서 만나면 그 자리에서 발견되는 정합성 문제(CORS, 토큰 매체, 응답 헤더, 에러 코드)는 디버깅 비용이 크다.

따라서 본 문서는 두 작업을 동시에 노린다.

1. **변경 동기화** — M1에서 바뀐 / 새로 노출된 / 미공개로 남은 API·DTO·헤더 계약을 FE가 미리 반영
2. **로컬 정합성 시험** — 로컬에서 BE(`localhost:8080`) ↔ FE(`localhost:5173`)를 실제로 연결해 7 시나리오를 통과시켜 두면 dev 첫 배포 시 정합성 이슈가 도메인·인증·CORS로 좁혀짐

대상 독자는 FE 저장소를 단독으로 책임지는 작업자(또는 Claude). BE 코드를 직접 안 봐도 본 문서만으로 작업을 완수할 수 있게 정보를 자기 완결적으로 담는다.

## 4. 응답 래퍼 · 에러 포맷 · 헤더 계약

### 4.1 성공 응답 — DTO 직접 (래퍼 없음)

현재 BE는 Controller마다 `ResponseEntity<T>`에 DTO를 직접 반환한다. `CLAUDE.md`에 언급된 `ApiResponse<T>` 래퍼는 **0.0.1v 시점에 일관 적용되어 있지 않다** (Open Question §8.1).

```jsonc
// POST /login → 200 OK
{
  "refreshToken": "eyJhbGc..."
}
// + Set-Cookie: access_token=<JWT>; Path=/; HttpOnly; SameSite=Strict
```

```jsonc
// POST /user → 201 Created
{
  "userEntityId": 12
}
```

```jsonc
// POST /api/v1/decks → 201 Created
{
  "deckId": 5,
  "name": "백엔드 기본",
  "parentDeckId": null,
  // ... DeckResponse.Create 필드 (BE DTO 직접 인용 — 변경 가능, Swagger UI 진실 소스)
}
```

### 4.2 에러 응답 — 전역 통일 (`{code, message, path, timestamp}`)

`GlobalExceptionHandler.errorResponse(...)` 라인 160-176 기준. **모든 4xx/5xx가 동일 스키마**.

```jsonc
// 401 Unauthorized — UNAUTHORIZED (USER002)
{
  "code": "USER002",
  "message": "인증이 필요합니다.",
  "path": "/user",
  "timestamp": "2026-06-25T16:42:11.234+09:00"
}
```

```jsonc
// 400 Bad Request — INVALID_INPUT (C001) — Bean Validation 실패
{
  "code": "C001",
  "message": "잘못된 입력 값입니다.",
  "path": "/user",
  "timestamp": "2026-06-25T16:42:11.234+09:00"
}
```

```jsonc
// 409 Conflict — DECK_NAME_DUPLICATE (DECK003)
{
  "code": "DECK003",
  "message": "이미 존재하는 덱 이름입니다.",
  "path": "/api/v1/decks",
  "timestamp": "2026-06-25T16:42:11.234+09:00"
}
```

**FE가 자주 분기할 ErrorCode 키** (전체는 `ErrorCode.java` 진실 소스):

| code | HTTP | 의미 | FE 분기 권장 |
| --- | --- | --- | --- |
| `C001` | 400 | 잘못된 입력 (Bean Validation) | 입력 폼 에러 강조 |
| `C002` | 404 | 일반 NOT_FOUND | 상위 분기 X (BC별 코드 우선) |
| `USER001` / `USER005` | 401/404 | 로그인 실패 (메시지 통일) | 보안상 동일 토스트 |
| `USER002` | 401 | 인증 필요 | refresh 시도 후 실패 시 세션 종료 |
| `USER003` | 409 | 이미 가입된 사용자 | 가입 폼 토스트 |
| `AUTH001` | 401 | 인증 토큰 누락 | 세션 종료 |
| `AUTH002` | 401 | 인증 토큰 만료 | **refresh 시도** (이미 인터셉터에 구현) |
| `AUTH003` | 401 | 인증 토큰 유효하지 않음 (위조/서명) | 세션 종료 |
| `AUTH004` | 401 | 토큰 사용자 없음 | 세션 종료 |
| `AUTH005` | 403 | 접근 권한 없음 | 권한 안내 |
| `AUTH101~104` | 400/401 | RT 관련 | 세션 종료 |
| `DECK001~006` | 다양 | Deck | 도메인 토스트 |
| `CARD001~033` | 다양 | Card | 도메인 토스트 |
| `LF001~004`, `LA001~004`, `LT001~003`, `LM001~007`, `TM001~002` | 다양 | LearningFacade 트리 | 도메인 토스트 |

### 4.3 헤더 계약

| 헤더 | 방향 | 동작 |
| --- | --- | --- |
| `X-Request-Id` | 양방향 | FE가 보내면 그대로 echo. 없거나 blank/256자 초과면 BE가 UUID 생성. **응답 헤더로 항상 회수**. |
| `Set-Cookie: access_token=...` | BE→FE | `POST /login` 응답에 자동. `HttpOnly; SameSite=Strict; Path=/`. dev=`Secure=false`, prod=`Secure=true`. |
| `Cookie: access_token=...` | FE→BE | 브라우저 자동 전송 (XHR/fetch `credentials: include` 필요) |

> **⚠️ CORS exposedHeaders 누락 이슈** — `SecurityConfig.corsConfigurationSource()` 라인 113에서 exposedHeaders가 `["Authorization", "Set-Cookie"]`만 등록되어 있다. **`X-Request-Id`가 빠져 있어 FE가 cross-origin 응답에서 헤더를 읽지 못한다**. 동일 오리진(dev에서 vite proxy 사용 시)이나 동일 호스트일 때만 읽힌다.
>
> **FE 동작 분기**:
> - vite dev server proxy 경유: BE 응답 헤더 그대로 노출됨 → FE에서 읽기 가능
> - vite proxy 미사용 + 직접 cross-origin 요청: 브라우저가 헤더 차단 → FE에서 못 읽음
>
> 본 문서는 vite proxy 경유 시나리오를 권장. 직접 cross-origin이 필요하면 섹션 8.4에 BE 측 조치 요구로 남김.

### 4.4 인증 매체 계약 (ADR009 요약)

| 토큰 | 매체 | TTL | FE 책임 |
| --- | --- | --- | --- |
| Access Token | HttpOnly Cookie (`access_token`) | 30분 | **읽지 않는다**. 브라우저가 자동 전송. Authorization 헤더 수동 부착 불필요 |
| Refresh Token | 응답 바디 (`{"refreshToken": "..."}`) | 7일 | **메모리에서만 보관** — localStorage/cookie 금지. 새로고침 시 유실 허용 (AT가 30분 살아있으므로 OK) |

### 5.2 axios response interceptor에 `X-Request-Id` 회수 로깅 추가

- [ ] `src/lib/api/client.ts` — response interceptor에서 응답 헤더 `X-Request-Id`가 있으면 ApiError 객체에 포함 + 콘솔 로깅 — Story 0-a 2-1로 BE가 모든 응답에 echo back하므로 5xx 디버깅 시 BE 로그 추적 키로 사용 — 의도적 5xx 한 건 발생시켜 콘솔에 requestId가 찍히는지 확인

**FE 권장 인터셉터 보강 (sketch)**:

```ts
// src/lib/api/client.ts (response interceptor 내부)
apiClient.interceptors.response.use(
  (res) => res,
  (err: AxiosError<ErrorResponseBody>) => {
    const requestId = err.response?.headers?.["x-request-id"];
    const body = err.response?.data;
    const apiError = new ApiError({
      code: body?.code ?? "UNKNOWN",
      message: body?.message ?? err.message,
      status: err.response?.status ?? 0,
      path: body?.path,
      timestamp: body?.timestamp,
      requestId,  // 신규
    });
    if (import.meta.env.DEV && requestId) {
      console.warn(`[api] ${apiError.status} ${apiError.code} requestId=${requestId}`);
    }
    return Promise.reject(apiError);
  },
);
```

> **CORS 주의** (섹션 4.3 박스): vite proxy 경유 시만 헤더 읽힘. 직접 cross-origin이면 `requestId = undefined`. proxy 설정은 섹션 6.2.

### 6.2 FE에서 BE 가리키기 (vite proxy 권장)

`X-Request-Id` 응답 헤더를 FE에서 읽으려면 **CORS exposedHeaders 이슈**(섹션 4.3)를 피해야 한다. 가장 간단한 회피책은 vite dev server proxy:

```ts
// third-tool-fe/untitled/vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      "/api": { target: "http://localhost:8080", changeOrigin: true },
      "/login": { target: "http://localhost:8080", changeOrigin: true },
      "/user": { target: "http://localhost:8080", changeOrigin: true },
      "/social": { target: "http://localhost:8080", changeOrigin: true },
      "/jwt": { target: "http://localhost:8080", changeOrigin: true },
      "/health": { target: "http://localhost:8080", changeOrigin: true },
      "/actuator": { target: "http://localhost:8080", changeOrigin: true },
    },
  },
});
```

proxy를 사용하면 FE 코드에서는 `VITE_API_BASE_URL=""`로 두고 상대 경로(`/login`, `/api/v1/decks`)로 호출. 헤더가 vite 서버를 통해 그대로 전달되어 `X-Request-Id` 회수 가능.

**대안**: vite proxy 미사용 + 직접 cross-origin. `VITE_API_BASE_URL=http://localhost:8080`, `credentials: "include"`. CORS allowed origin에 `localhost:5173` 포함되어 인증·쿠키는 OK. 단, `X-Request-Id`는 못 읽음.

```bash
# FE 저장소 (third-tool-fe/untitled)
npm install
npm run dev
# → http://localhost:5173
```

### 8.2 AI Suggestion Controller 노출 시점

Story 3 2-1·2-2(본주)는 Port + Static Adapter만. Controller 노출은 **M2 Epic 3**에서 LLM 어댑터(Spring AI ChatClient)와 묶어 진행 (`product-aisuggestion.md`). 0.0.2v 인계서에서 endpoint shape 공식 예고 예정. FE는 그때까지 호출 X.

### 8.3 FE staging/prod 도메인의 BE CORS 등록

본주에 dev 배포는 발생하지만 FE staging 호스트는 아직 미확정. BE `SecurityConfig.corsConfigurationSource()`는 `https://thirdstool.com` 1개 prod 도메인만 등록. FE staging이 별도 호스트면 BE 측에 추가 요청 필요.

### 8.4 CORS exposedHeaders에 `X-Request-Id` 추가 (BE 측 조치)

섹션 4.3에서 본 이슈. FE가 vite proxy 없이 직접 cross-origin 호출 시 헤더 못 읽음. BE 측 한 줄 추가로 해결:

```java
// SecurityConfig.java 라인 113 근처
configuration.setExposedHeaders(List.of("Authorization", "Set-Cookie", "X-Request-Id"));
```

본 변경은 BE 책임. FE 측에서 0.0.2v 인계서 요청 항목으로 기록.

### 8.5 RT 메모리 보관의 새로고침 UX

FE 현재 정책(메모리 보관, ADR009 결정). 새로고침 직후 RT 유실 → AT 만료 시 재로그인. UX 개선은 별도 product 이슈로 분리(BE 변경 동반 가능). 본 인계 범위 외.

### 8.6 `/actuator/prometheus` ↔ FE Grafana 대시보드

BE 측 ops 작업. FE는 인지만. Grafana docker-compose(`monitoring/`)는 BE 인프라이며 FE 코드 영향 없음.
