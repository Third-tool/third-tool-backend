# Curation Rules

> **목적**: 백엔드 개발자 포트폴리오·자소서에 올릴 재료를 큐레이션하는 **규칙 박음**.
> 재료 창고는 `milestones/version/{Nv}/` (박제 결과) + `living-docs/` (현재 자산 인덱스) + `topologys/` (수평 규칙 pin). 여기 `quration/`은 그 위에서 **면접·자소서용 발췌·서사·선정**을 담당.
> **원칙**: 원본은 창고에 그대로 두고, 여기는 **참조 링크 + 큐레이션 서사**만.

---

## 1. 등재 트리거 (어떤 걸 후보로 볼 것인가)

다음 중 **하나 이상** 해당하면 후보 등재 대상:

| # | 트리거 | 예시 |
| --- | --- | --- |
| T1 | **결정 + 대안 + trade-off**가 명확히 있음 (ADR 성격) | ADR021 Axis Soft Delete 승격 — hard delete vs soft delete 대안 비교 있음 |
| T2 | **수치·성능 지표·배포 리스크**가 걸린 결정 | V19 3-phase — 무중단 배포 리스크 관리 |
| T3 | **도메인 통찰**이 있는 모델링 (헥사고날·DDD·불변식 강제) | AI 6-Port + Static/LLM Adapter 스왑, concepts[] Aggregate 확장 |
| T4 | **프로덕션 이슈 근본원인 추적**이 있는 것 | "카드 만들 때 축 인식 실패" → orphanRemoval hard delete 원인 규명 |
| T5 | **인프라·보안 아키텍처 결정** (조직 표준화 가치) | OIDC AssumeRole 전환, VPC 3-layer, ECS Task Role 3종 분리 |
| T6 | **협업·프로세스 개선** (재사용 가능한 관행) | ADR 관행, workflow 3구간 규칙, Reviewer 5관점 세션 |

**후보에서 제외하는 것**:
- 단순 CRUD 구현 (기술 결정 없음)
- 개인 취향 리팩토링
- 시장 표준 그대로 따른 것 (예: 기본 Spring Boot 설정)

## 2. 후보 등재 형식 (blended STAR + 트레이드오프)

각 후보는 아래 형식 준수. 원본 서사가 있어도 여기는 **면접관 10초 파악용** 압축.

```markdown
## [{milestone}-{seq}] {제목}  `[{theme1} · {theme2}]`

**훅**: {한 줄. 왜 재미있는지 · 무엇을 해결했는지}

**S (상황)**: {배경 · 제약 · 규모}
**T (과제)**: {요구사항 · 목표}
**A (행동)**: {접근 · 구현 · 핵심 단계}
**R (결과)**: {수치 · 산출물 · 정합성 확보}

**Trade-off**: {선택하지 않은 대안 · 이유 · 비용}

**지표**: {있으면 성능·비용·시간 수치}

**참조**: {ADR / Flyway / Story / 코드 파일 · 라인}

**상태**: `[ ] 후보  [ ] 선정  [ ] 보류`
```

### 필드 규칙
- **milestone**: `0.0.1v`, `0.0.2v` 등. 여러 버전에 걸친 경우 시작 버전 기준.
- **seq**: milestone 내 후보 등재 순서 (2자리 zero-pad, `01`, `02` …).
- **제목**: 명사구, 20자 내외. 검색 가능한 키워드.
- **theme**: `themes.md`의 8개 중 1~2개 선택. 3개 이상은 금지 (초점 흐림).
- **훅**: 30자 이내. 면접관/독자 attention grabber.
- **S/T/A/R**: 각각 1~3줄. 전체 12줄 이내 지향.
- **Trade-off**: 필수. 없으면 이 후보는 "결정" 성격이 부족 — 재검토.
- **지표**: 선택. 있으면 강력한 재료.
- **참조**: 원본 소스 링크 (ADR·Flyway·Story·코드).
- **상태**: 후보(default) → 선정 → 보류. 하나만 체크.

## 3. 선정 우선순위 (selected.md에 올릴 순서 결정)

동점이면 상위 기준 우선.

| 우선순위 | 기준 | 이유 |
| --- | --- | --- |
| P1 | **수치·지표가 강한 결정** | 면접관 신뢰도 즉시 상승 |
| P2 | **여러 theme에 걸친 결정** | 폭 넓은 사고 어필 |
| P3 | **최근 milestone에서 나온 것** | 현재 실력 반영 |
| P4 | **근본원인 추적 서사**가 있는 것 | 문제해결 능력 스토리텔링 |
| P5 | **재사용 가능한 관행** (팀·조직 표준화) | 리더십·시스템 사고 어필 |

각 자소서 지원 시 상위 5~7개 정도 선정 지향 (너무 많으면 초점 흐림).

---

## 4. Theme 태깅 규칙

- **1~2개만**. 3개 이상 태깅은 초점 흐림 → 나눠서 후보 2개로.
- 카탈로그는 `themes.md`. 새 theme 추가는 최소화 (8개 안정 유지).
- 태그 순서: **primary theme 먼저**. 예: `[DB · 무중단운영]`이면 DB가 주.

---

## 5. 상태 라이프사이클

```
[ ] 후보           ← 등재 시 default
     │
     ├─ (선정 결정) ──▶  [x] 선정   ← selected.md에 편입
     │
     └─ (탈락 결정) ──▶  [x] 보류   ← 재사용 여지 남김, 삭제 X
```

- **후보** → 등재 시 기본. 아무 판단 안 함.
- **선정** → 자소서 지원 시점에 선택. selected.md에 정리.
- **보류** → 이번 지원엔 안 넣지만 다음엔 넣을 수도 있음. 삭제하지 않음.

---

## 6. 재활용 · 갱신 규칙

- **원본 서사 변경 시** (원본 milestones/ADR 갱신) → 여기 후보 항목의 참조 링크만 재검증, 서사 최신화.
- **후보 삭제** 원칙적으로 하지 않음. 상태를 "보류"로 옮김 (역사 보존).
- **selected.md**는 지원할 때마다 재작성 가능 (스냅샷).
